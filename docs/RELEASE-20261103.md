## Bounded static-file recovery

The candidate now retries one network request after 250 ms when a known,
query-free same-build static JS/CSS asset returns 404, 502, 503 or 504. The retry
bypasses HTTP cache and preserves request credentials/mode. It never substitutes
an older cached module for an HTTP error. Persistent errors and a rejected retry
remain errors; 401/403, 429/500, backend/dynamic paths, cross-origin/sibling-build
paths and query-bearing URLs are not retried. Existing offline fallback behavior
is retained. This is not a new atomic version-pinning scheme: it avoids adding
mixed-cache module recovery to the existing worker.

The startup notice includes an explicit full-page retry for cold first-load failures
before a worker controls the page. It does not clear caches or storage, automatically
reload, or re-evaluate a partially loaded module graph in place.

Additional final validation:

- `node dev/tests/static_retry_test.mjs`: 40 actual-worker-handler groups across both
  builds, covering retry bounds, eligible status codes, auth/backend/query/scope
  exclusions, rejected retry, no HTTP-error cache substitution and offline fallback.
- `python3 dev/tests/static_retry_browser_test.py`: 16 rendered groups across both
  builds. Transient 503/404 recovers in two network attempts with 30 cards and working
  Start/scoring, even with a deliberately unusable cached module. Persistent
  503/404 stays visible after two attempts; 401/403 stays visible after one. Manual
  recovery resumes the saved game. Cold first load, evicted cache and subsequent
  offline recovery pass. No automatic reload/request loops occur.
- `python3 dev/tests/scorer_upgrade_test.py`: interrupted candidate install retains
  the previous active worker/cache and running game; subsequent successful update,
  offline reload and saved-data isolation pass.
- All 18 startup/simple-scoring groups per build and ES5 syntax checks were rerun
  after adding the manual retry button; production artifact audit and both offline
  module graphs remain required final checks.

## Selector finding and remaining limits

Before mitigation, a synthetic HTTP 503 for registry.js reproduces blank game cards with a warm cache;
refresh after recovery restores all 30 cards without changing the saved game.
The worker returns resolved non-OK responses and falls back only on rejected fetches.
This is a confirmed mechanism, not a confirmed diagnosis of the reported Pixel
incident. The bounded network retry now mitigates a transient response that recovers on the
second attempt. Persistent/unrecoverable failures deliberately remain visible,
with explicit manual recovery. Ordinary startup and the tested update/offline path pass.

Direct live retrieval from this cloud environment receives HTTP CONNECT 403 under
its enforced network policy. Exact-commit GitHub Pages success must be reported
separately; it does not constitute direct live-content or physical-device verification.
